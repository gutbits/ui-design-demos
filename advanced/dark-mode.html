🌓 Dark Mode

Designing for light and dark — why a good dark theme is engineered, not inverted. Elevation, desaturation, contrast pitfalls, and the CSS that ties it together.

Why Dark Mode Is Not "Just Inverted"

Flipping #fff ↔ #000 produces a harsh, vibrating, unusable theme. A real dark mode is a separately designed system with its own rules for contrast, color, and depth.

The naive approach (don't do this)

/* ❌ Pure inversion — high glare, halation, eye strain */ body { filter: invert(1); } /* or */ body { background: #000; color: #fff; }

Problems with naive dark mode:

  • Pure black + pure white creates the maximum 21:1 contrast ratio. On OLED this causes halation — text appears to bleed and smear, especially for people with astigmatism.
  • Saturated brand colors that looked fine on white "vibrate" against dark backgrounds and feel neon.
  • Shadows disappear. In light mode depth comes from shadows; on a dark surface a shadow is invisible, so the whole depth language breaks.
  • Images and illustrations with white backgrounds become glaring rectangles.
Rule of thumb: use a very dark gray, not black, for the base (Material recommends #121212), and pull text back from pure white to roughly rgba(255,255,255,0.87) for primary text.

Elevation: Lighter Surfaces, Not Shadows

In light mode, things closer to the user cast bigger shadows. In dark mode, that cue inverts: the closer a surface is, the lighter it gets, as if it catches more ambient light.

Material Design models this with semi-transparent white overlays whose opacity grows with elevation. The base is #121212; each elevation level adds a white film:

/* Elevation via a tunable white overlay on the dark base */ .surface { background-color: #121212; background-image: linear-gradient( rgba(255,255,255,var(--elev, 0)), rgba(255,255,255,var(--elev, 0)) ); } .surface.card { --elev: 0.05; } .surface.dialog { --elev: 0.07; } .surface.menu { --elev: 0.12; }

You can still add a soft shadow in dark mode, but it does little work — keep it subtle and let the surface lightening carry the hierarchy.

Desaturate Your Colors

Highly saturated colors against dark backgrounds optically vibrate and fail contrast. Lower the saturation and lift the lightness of accents for dark mode.

The left swatch in each pair is the original light-mode brand color; the right is its dark-mode-tuned version (saturation reduced, lightness raised). Notice the right column sits more calmly on the dark surface.

/* Tune an accent for dark mode in HSL space */ :root { --brand: hsl(248, 85%, 60%); } /* light mode */ @media (prefers-color-scheme: dark) { :root { --brand: hsl(248, 60%, 72%); } /* −sat, +light */ }
Why it works: our eyes adapt to a dark surround by widening the pupil; saturated hues then over-stimulate and "buzz". Reducing chroma and raising lightness restores legibility and calm.

Contrast Pitfalls

Dark mode has its own accessibility traps. WCAG still applies — but the failure modes differ from light mode.

  • Halation from too much contrast. Pure-white text on pure-black is technically 21:1 but physically uncomfortable. Aim for primary text around rgba(255,255,255,0.87) on a #121212–#1e1e1e base.
  • Disabled / secondary text vanishing. On dark, low-opacity gray text easily drops below the 4.5:1 AA threshold. Verify every tier (primary, secondary, disabled) against its actual surface — including elevated ones.
  • Elevated surfaces change the math. Text that passes on the base may fail on a lighter elevated card. Test against the lightest surface the text can land on.
  • Colored text & links. A blue link that passes on white usually fails on dark. Use the desaturated, lightened variant.
  • Focus rings & borders. Thin 1px borders that read on white disappear on dark; bump opacity or use a subtle inner glow.

The CSS: prefers-color-scheme + variables + toggle

A production-grade theming setup has three layers: respect the OS preference, store an explicit user override, and theme everything through CSS custom properties.

1. Declare support & respect the OS

/* Tell the UA both schemes exist → themed form controls, scrollbars */ :root { color-scheme: light dark; } /* Default tokens = light; override under the dark media query */ :root { --bg: #ffffff; --text: #1b1e28; --surface: #f5f6fb; --accent: hsl(248,85%,60%); } @media (prefers-color-scheme: dark) { :root { --bg: #121212; --text: rgba(255,255,255,0.87); --surface: #1e1e1e; --accent: hsl(248,60%,72%); } }

2. Let an explicit choice win via a data-attribute

/* User override on <html data-theme="..."> beats the media query */ html[data-theme="light"] { --bg: #fff; --text: #1b1e28; } html[data-theme="dark"] { --bg: #121212; --text: rgba(255,255,255,.87); }

3. Wire it up — and persist the choice

const root = document.documentElement; // Restore saved choice on load (falls back to OS preference) const saved = localStorage.getItem('theme'); if (saved) root.dataset.theme = saved; btn.addEventListener('click', () => { const isDark = getComputedStyle(root) .getPropertyValue('--bg').trim() === '#121212'; const next = isDark ? 'light' : 'dark'; root.dataset.theme = next; localStorage.setItem('theme', next); });
Avoid the flash (FOUC): read localStorage and set data-theme in a tiny blocking <script> in the <head>, before the body renders, so the page never paints the wrong theme first.
