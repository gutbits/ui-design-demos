Parallax Scrolling

Creating depth from motion — when background and foreground scroll at different speeds, flat pixels gain a third dimension. Pure-CSS, background-attachment, and JS approaches, with the performance and accessibility caveats that matter.

The Idea: Differential Scroll Speed

Parallax is a depth cue borrowed from the real world: look out a moving car window and nearby fence posts whip past while distant mountains drift slowly. Move things at different speeds and the brain infers distance.

On the web we exploit this by making background layers travel slower than foreground content as the user scrolls. There are three practical techniques, each with trade-offs:

  • CSS 3D transform — perspective + translateZ on a scroll container. Smooth, GPU-driven, no JS, but constrains layout.
  • background-attachment: fixed — the simplest "the background holds still" effect. One line of CSS; limited and janky on mobile.
  • JS scroll listener — read scroll position, transform layers. Total control, but you must guard performance and reduced-motion.

This panel scrolls at full speed while the gradient field behind it lags, creating depth. The depth amount is set purely by how far back each layer is pushed in Z and how much it's scaled to compensate.

Because the browser composites the 3D transform on the GPU, this stays smooth even on long pages — there's no scroll event handler firing per frame.

/* The scroll container becomes a depth "lens" */ .viewport { height: 100vh; overflow-y: auto; perspective: 8px; /* smaller = stronger depth */ perspective-origin: 0 0; } .group { transform-style: preserve-3d; position: relative; } /* Push back in Z, then scale up so it still fills the frame. Farther layers move slower relative to the scroll. */ .layer-back { transform: translateZ(-12px) scale(2.5); } .layer-front { transform: translateZ(0); }
The scale compensation rule: a layer at translateZ(-n * perspective) appears (perspective + n*perspective)/perspective times smaller, so multiply its scale by 1 + n to refill the frame. Here perspective is 8px; a layer at -12px scales by ~2.5.

Technique 2 — background-attachment: fixed

The quickest parallax-ish effect: pin a background to the viewport so page content scrolls over a stationary image. Scroll the whole page and watch the band below hold its gradient still.

background-attachment: fixed
.hero { background-image: url(scene.jpg); background-attachment: fixed; /* viewport-locked */ background-size: cover; background-position: center; }

It's one property, well supported on desktop, and needs zero JS. But it has real limits:

  • Mobile is rough. iOS Safari and many Android browsers don't repaint a fixed background per frame, so it stutters or simply ignores fixed (falling back to scroll).
  • It's not true multi-speed parallax — the background is fully static (speed 0), not "slower". You get a single fixed plane, not layered depth.
  • Repaint cost on large images can hurt scroll performance even on desktop.

Technique 3 — JS Scroll-Driven Parallax

For arbitrary, multi-speed depth, drive layer transforms from scroll position. Scroll the whole page — the moon, stars, and two mountain ranges below move at different rates as this section passes through the viewport.

JS-driven multi-layer parallax
/* Read scroll once per frame via requestAnimationFrame — never transform directly inside the scroll event (causes jank). */ const layers = [ { el: stars, speed: 0.15 }, { el: moon, speed: 0.30 }, { el: mtnFar, speed: 0.45 }, { el: mtnNear, speed: 0.70 }, ]; let ticking = false; function onScroll() { if (ticking) return; ticking = true; requestAnimationFrame(() => { const rect = stage.getBoundingClientRect(); const progress = -rect.top; // px scrolled past the stage top for (const { el, speed } of layers) { el.style.transform = `translate3d(0, ${progress * speed}px, 0)`; } ticking = false; }); } window.addEventListener('scroll', onScroll, { passive: true });
Always use translate3d / translateZ (not top/margin) so the browser promotes layers to their own GPU composite layer and skips layout/paint on every frame.

Performance Caveats

Parallax is one of the easiest ways to wreck scroll performance. A janky 30fps hero feels worse than no effect at all.

  • Never transform inside the scroll event directly. Throttle through requestAnimationFrame and a ticking flag so you do at most one update per frame.
  • Mark scroll listeners { passive: true } so the browser doesn't wait to see if you'll preventDefault — this keeps scrolling on the compositor thread.
  • Animate only transform and opacity. These are compositor-only properties; animating top, left, or background-position forces layout/paint each frame.
  • Use will-change: transform sparingly on moving layers — it hints the browser to pre-promote them, but over-using it wastes GPU memory.
  • Watch filter: blur() and huge images. Blurred or oversized parallax layers are expensive to recomposite; keep them small.
  • Prefer the CSS perspective technique when the layout allows — it has no JS and runs entirely on the compositor.

Accessibility: prefers-reduced-motion

Parallax can trigger motion sickness, dizziness, and vestibular disorders. Respecting the OS "reduce motion" setting isn't optional — it's a core accessibility requirement.

Honor it in both CSS and JS:

/* CSS: neutralise the effect for users who asked for less motion */ @media (prefers-reduced-motion: reduce) { .layer-back, .layer-mid { transform: none !important; } .bg-fixed { background-attachment: scroll; } }
// JS: skip the scroll handler entirely when reduced motion is on const reduce = window.matchMedia('(prefers-reduced-motion: reduce)'); if (!reduce.matches) { window.addEventListener('scroll', onScroll, { passive: true }); } // And re-check if the user changes the setting at runtime reduce.addEventListener('change', syncMotionPreference);
Note: the JS demo above already checks prefers-reduced-motion — if your system has "reduce motion" enabled, those layers are held still on purpose.
