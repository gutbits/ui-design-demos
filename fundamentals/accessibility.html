Accessibility

Accessible design isn't a feature you bolt on — it's how you build for the full range of human ability. Master WCAG 2.2, contrast, ARIA, keyboard navigation, and motion preferences.

WCAG 2.2 — The Foundations

The Web Content Accessibility Guidelines are organized around four principles, remembered as POUR. Every success criterion supports one of them.

P

Perceivable

Information must be presentable in ways users can perceive — text alternatives, captions, sufficient contrast.

O

Operable

Interface and navigation must be operable — keyboard access, enough time, no seizure-inducing flashes.

U

Understandable

Content and operation must be understandable — readable text, predictable behavior, helpful errors.

R

Robust

Content must be robust enough to work with current and future tools, including assistive technologies.

Conformance Levels

Each criterion is graded A, AA, or AAA. AA is the practical target for most products and the level referenced by laws like the ADA, EN 301 549, and Section 508.

A

Minimum

Essential. Without it, some groups cannot use the content at all (e.g. keyboard operability, text alternatives).

AA

Standard target

The legal and industry benchmark. Adds 4.5:1 text contrast, resizable text, consistent navigation.

AAA

Enhanced

Highest bar (7:1 contrast, sign language for video). Aspirational; rarely required site-wide.

New in WCAG 2.2 (2023): nine added criteria including Focus Not Obscured, Dragging Movements (offer a non-drag alternative), Target Size (Minimum) of 24×24 CSS px, and Accessible Authentication. Reference: w3.org/TR/WCAG22.

Color Contrast (Live)

Contrast ratio measures the luminance difference between text and its background. WCAG AA requires 4.5:1 for normal text and 3:1 for large text (≥24px, or ≥18.66px bold). AAA requires 7:1. Adjust the colors and watch the verdict update.

Beyond text: WCAG 2.1+ also requires 3:1 contrast for UI components and graphical objects — icons, input borders, focus indicators, and chart elements. Color must never be the only way information is conveyed (the "use of color" criterion).

Focus States

A visible focus indicator tells keyboard and switch users where they are on the page. Removing it (outline: none) with no replacement is one of the most common — and most damaging — accessibility mistakes. Tab through both columns to compare.

✗ Focus removed (don't do this)

With outline:none and no substitute, a keyboard user is lost.

✓ Clear focus ring

A 3px outline with outline-offset is unmistakable.

Use :focus-visible: it shows the ring for keyboard navigation but not for mouse clicks, giving you the best of both. WCAG 2.2 also adds Focus Appearance (the indicator must be large and high-contrast enough) and Focus Not Obscured (sticky headers must not hide the focused element).

Keyboard Navigation

Everything achievable with a mouse must be achievable with a keyboard alone. Many users — motor-impaired, blind, or simply power users — never touch a pointer.

Tab / Shift + TabMove forward / backward through focusable elements.
EnterActivate links and buttons; submit forms.
SpaceActivate buttons, toggle checkboxes, scroll the page.
Arrow keysMove within a composite widget — menus, radios, tabs, sliders.
EscClose dialogs, menus, and popovers.
Golden rules: (1) Use native <button>, <a>, and <input> — they're keyboard-accessible for free. (2) Keep a logical tab order (follow the DOM; avoid positive tabindex). (3) Provide a "Skip to content" link so users can bypass repeated navigation. (4) Never trap focus except inside an open modal.

ARIA & Screen Readers

Screen readers announce the page through its semantic structure. The first rule of ARIA is: don't use ARIA when a native HTML element will do — semantic HTML is accessible by default. Reach for ARIA only to fill gaps.

Native semantics first — these convey role, name, and state automatically
<!-- Good: the browser already knows this is a button -->
<button type="submit">Save changes</button>

<!-- Landmarks let users jump between regions -->
<nav aria-label="Primary"> ... </nav>
<main> ... </main>
When native HTML falls short — use ARIA to add the missing semantics
<!-- An icon-only button needs an accessible name -->
<button aria-label="Close dialog">✕</button>

<!-- Communicate a custom toggle's state -->
<button aria-pressed="true">Mute</button>

<!-- Announce dynamic updates without moving focus -->
<div role="status" aria-live="polite">Saved!</div>

<!-- Decorative images get an empty alt so SRs skip them -->
<img src="swirl.svg" alt="">
Always provide an accessible name for interactive elements (visible text, aria-label, or aria-labelledby), and meaningful alt text for informative images. Common roles: button, navigation, dialog, alert, status, tab/tabpanel. Full reference: MDN ARIA and the ARIA Authoring Practices Guide.

Respecting Motion Preferences

Animation can cause nausea, dizziness, and migraines for users with vestibular disorders. Operating systems expose a "reduce motion" setting; honor it with the prefers-reduced-motion media query.

Live demo — this spins, unless your OS requests reduced motion

Enable "Reduce motion" in your OS accessibility settings, then reload — the box will hold still.

@media (prefers-reduced-motion: reduce) {
  * { animation: none !important; transition: none !important; }
}
Design motion-safe by default: prefer subtle fades over large parallax or zoom. Provide essential motion (like a loading spinner) but strip decorative, distance-covering animation when reduction is requested. See MDN: prefers-reduced-motion.
